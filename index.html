How to Solve a Problem: The Google Engineering Framework

A systematic mental blueprint outlining the required phases of thought, analysis, verification, and code construction for technical interviews.

Phase 01

Problem Interrogation & Constraint Discovery

Never begin designing or writing code immediately. Spend the first 3 to 5 minutes clarifying ambiguities with the interviewer. Formulate explicit questions to uncover hidden assumptions:
  • Input Bounds & Scale: What is the maximum value of $N$? (If $N \le 10^5$, an $O(N \log N)$ or $O(N)$ solution is required; if $N \le 20$, backtracking/exponential is acceptable).
  • Value Types & Ranges: Can values be negative? Are integers signed 32-bit or 64-bit? Can values exceed standard integer overflow limits?
  • Duplicates & Ordering: Are elements strictly unique, or can duplicates occur? Is the input ordered, partially ordered, or random?
  • Memory & Scale Constraints: Does the input fit entirely in main memory, or must this stream from external storage/disk?
Phase 02

Test Case Generation (Base, Typical, Adversarial)

Construct at least three representative test cases manually before proposing algorithms:
  • Base Case / Degenerate Input: $N = 0$ (empty collection), $N = 1$ (single element), or minimal valid input boundary.
  • Standard Non-Trivial Case: A representative general example that requires non-trivial processing (e.g., 5 to 7 elements with varying values).
  • Adversarial / Edge Case: Inputs designed to break naive assumptions: all identical elements, sorted in reverse order, negative numbers, disconnected graphs, or cyclic dependencies.
Phase 03

Baseline Solution & Bottleneck Identification

State the brute-force or naive solution explicitly and compute its Big-O time and space complexity ($O(N^2)$, $O(2^N)$).
  • Analyze why the naive solution is inefficient: Where is repetitive or redundant work being computed?
  • Look for unneeded recalculations, repeated linear scans, or duplicate subtree evaluations. Pinpoint the specific operational bottleneck.
Phase 04

Pattern Matching & Invariant Selection

Identify the governing algorithmic pattern that eliminates the bottleneck:
  • Contiguous Subarray / Window: Sliding Window (fixed/dynamic length) or Prefix Sum frequency mapping.
  • Sorted Sequence: Two Pointers (converging/parallel) or Binary Search on index/answer space.
  • Monotonic Traversal: Next greater/smaller element queries using a Monotonic Stack or Monotonic Deque.
  • Dependencies & Topological Ordering: Directed Acyclic Graph (DAG) with Kahn's BFS or DFS cycle detection.
  • Shortest Path on Weighted Graphs: Dijkstra (non-negative weights), Bellman-Ford (negative edges), or BFS for unweighted graphs.
  • Disjoint Partitioning & Connectivity: Union-Find (Disjoint Set Union) with path compression and rank.
  • Prefix Queries & String Dictionaries: Trie (Prefix Tree) with character branching.
  • Optimal Substructure with Overlapping Subproblems: Dynamic Programming (Tabulation bottom-up or Memoization top-down).
Phase 05

Big-O Complexity Derivation & Interviewer Alignment

Before typing code, verbally walk the interviewer through the proposed algorithm and formally state:
  • Time Complexity: $O(T)$ in terms of vertices $V$, edges $E$, or input size $N$, proving each step's bound.
  • Space Complexity: $O(S)$ auxiliary memory, accounting for recursion stack depth, hash tables, and data structure allocations.
  • Obtain explicit verbal confirmation from the interviewer: "Does this approach align with your expectations before I implement it?"
Phase 06

Production-Grade Code Construction

Implement the solution following standard Google software engineering guidelines:
  • Modular Structure: Decompose large procedures into concise, single-responsibility helper functions.
  • Explicit Naming: Use descriptive variable identifiers (e.g., prefixSumCounts rather than m; leftBound rather than l).
  • Defensive Guard Clauses: Validate null, empty, or single-element inputs at the function entry point.
  • Avoid Global State: Keep variables properly scoped without side-effects.
Phase 07

Mental Dry Run & Line-by-Line Tracing

Do not execute or announce completion immediately upon typing the last line. Step through your code line-by-line:
  • Trace a non-trivial sample input using a state tracking table (listing pointer positions, current loop index, and variable values).
  • Check boundary indexes (0, n - 1, mid - 1, mid + 1) to prevent off-by-one errors.
  • Verify loop termination invariants and recursion base cases.
Phase 08

Post-Mortem & Generalized Takeaways

Conclude the exercise by articulating how the solution scales and records lessons for long-term memory:
  • Could memory usage be reduced from $O(N)$ to $O(1)$ by mutating pointers or rolling variables?
  • What general family of problems does this technique solve?
  • Log the core insight into your preparation notes and schedule spaced reviews.
